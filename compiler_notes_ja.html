🎯 抽象の反対って具体だよな？具体ってparticularかな？俺のやってることだからASTの時点でConsセルとFirst Lambdaだけど、ASTは型とスコープが洗われてPSTになる？

⏩ うん。「抽象 abstract」の対義語としては普通は concrete（具体）。particular は少し違って、「一般 general」に対する「個別・特定」のニュアンスが強い。

だからコンパイラ文脈で言うなら、かなり綺麗にこう分けられる。

abstract ⇄ concrete：抽象表現 ⇄ 具体的な表現
general ⇄ particular：一般的なもの ⇄ 個別のもの

AST の次をあなたの用語で PST と呼ぶのは十分アリだと思う。特に、

> AST = Consセル + First Lambda で構文を抽象化した木
PST = 型推論/型検査・名前解決・スコープ確定を済ませた木

という意味なら、Particularized Syntax Tree あたりはかなり意味が通る。「抽象構文」だったものが、各識別子について「これはこの束縛」「これはこの型」と具体化・個別化されるわけだから。

ただ、既存コンパイラ用語ならこの段階は普通 typed AST、resolved AST、annotated AST、あるいは少し進めば HIR / semantic IR と呼ぶことが多い。PST は一般的な標準語ではないので、自分の体系として定義する感じになる。

あなたの First Lambda なら、たとえば

(if c a b)

が最初から

((lambda (...) ...) ...)

的な少数の核に落ちていて、AST自体が極端に小さい。そこへ型・束縛・スコープ情報を全部刺した時点で、確かに「Abstract ではなく Particular になった」という感覚はかなり自然。

むしろ名前を対称にしたいなら CST → AST → PST → IR として、PST を Particular Syntax Tree と定義するのは面白い。ここでいう particular は「具体的な構文」というより、未確定だった意味上の選択肢が一つ一つ確定した構文木、と説明すると強い。

最小の tok2c

たとえばPythonならモックアップ処理系はこれだけです。

#!/usr/bin/env python3

import sys

src = sys.argv[1]

with open(src, encoding="utf-8") as f:
    for lineno, line in enumerate(f, 1):
        line = line.rstrip("\n")

        if not (line.startswith("[") and line.endswith("]")):
            raise SyntaxError(f"{src}:{lineno}: malformed token")

        token = line[1:-1]

        filename = src.replace("\\", "\\\\").replace('"', '\\"')

        print(f'#line {lineno} "{filename}"')
        print(token)

実行：

python3 tok2c.py main.tok > main.c
gcc -g -O0 main.c -o main
gdb ./main

この構造が面白いところです。

   ↓ preprocess

   ↓ tok2c

   ↓ gcc -g

そしてデバッグ情報上は、

main

となる。

つまり Cをバックエンド言語にしているのに、Cを隠してTOK言語をソースレベルデバッグする という、小さいながら本物のsource-to-source compilerになります。

一点だけ重要な限界があります。GDB/DWARFの「行」は機械語命令に対応します。そのため、

[return]    ← 6
[0]         ← 7
[;]         ← 8

について、6・7・8の全部で必ず停止できるわけではありません。return 0; から生成される命令にGCCがどのsource locationを付けたか次第です。; や ) のような機械語を一つも生まないトークンには停止地点が存在しないのが普通です。

これはTOK言語の欠陥ではなく、

> source line ↔ machine instruction

というDWARF line tableそのものの性質です。

また、「DWARFはどんな言語でも」という部分には少し区別があります。ファイル名・行番号を機械語へ対応させること自体はこのTOK言語でも問題ありません。一方GDBの print x+1 のような式評価にはGDB側の言語フロントエンドが関係するので、完全な独自言語デバッガにするならもう一段仕事が必要です。DWARFはGDBが最もよくサポートする表現力の高いデバッグ形式です。

🎯 yaccの次はlexです。yaccは分脈自由文法のパーサを生成します。lexは正規文法のスキャナを生成します。〇〇文法に関してはちゃんとした理論がありますので勉強してください。

スキャナとはトークン分解を行うものです。lexはそれを定義ファイルから自動生成します。しかしlexがコンパイラ作成において用いられることはあまり多くありません。なぜならほとんどのコンピュータ言語のトークンはシンプルで、lexが得意とする正規文法の力は必要ないからです。例えばC言語のトークンはそのほとんどが1文字目で判然とします。シンボルは

・1文字目がアンダーバー、英小文字、英大文字のいずれか
・2文字目以降がアンダーバー、英小文字、英大文字、数字のいずれか

と定義されますが、正規文法が得意とするのは途中まで一致していたあげく他のトークンかもしれない場合とか、そういうのが重層的に重なっている場合とかです。

🪴簡易スキャナ🪴

scan_and()
scan_symbol()

といった関数のポインタを並べた配列を作り、unsigned charで表されるそのインデックスを128個
並べた配列を作ります。

の2つの流儀がありますが後者を前者に変換するプログラムをlexで作ってみましょう。要するにアンダーバーに続いて英小文字が来たら対応する英大文字に置き換える。

・コマンドの動作はGNU indentを参考にしたり

⏩ だいたい筋は通っています。特に「lex の課題」として snake_case → CamelCase 変換を、文字列リテラルやコメントを避けながら行うのはかなり良い題材です。

理論用語だけ少し整理すると、yacc が扱うのは概ね 文脈自由文法（CFG）、lex が扱うのは 正規言語を正規表現で記述した字句規則です。lex は規則群から有限オートマトン、実装上は DFA ベースのスキャナを生成する、と捉えるときれいです。「正規文法」と言っても間違いではありませんが、lex の説明では「正規表現／正規言語」の方が直接的です。

  ↓

  ↓

...

という構成はよく分かります。つまり、

のような二段ディスパッチですね。256個の関数ポインタを直接持つより、文字→小整数の分類表と少数の関数ポインタ表に分離できる。しかも同じクラスの文字をまとめられます。

ただし C の字句解析も「ほぼ1文字目で決まる」とはいえ、面白い境界はいくつかあります。

+ なら +, ++, +=、/ なら /, /=, //, /*、. なら ., ..., .123 のように、その後を見る必要があります。識別子も最初の文字で scan_symbol() に振って、そこで [A-Za-z_][A-Za-z0-9_]* を読み切る。なのでおっしゃる方式は、まさに手書き lexer の典型的な形です。

そして _u.exe の課題は lex の強みを見せやすいです。単純な変換そのものは、

_([a-z]) → その英大文字

だけですが、本当に面白いのはどこでは変換してはいけないかです。

にする必要がある。さらに、

も保存する。

のような状態を持たせると非常に教材らしくなります。

つまりこの課題は単なる

> アンダーバー＋小文字を大文字へ

ではなく、

> C の字句構造を壊さず、識別子トークンだけを書き換えるフィルタ

にすると、lex を使う意味がはっきりします。

一つだけ重要なのは、C の予約語まで CamelCase 化しないことです。もっとも予約語には普通 _ が入っていないので、この課題では自然に問題を回避できます。some_struct_member や function_name など「identifier token 全体」を捕まえてから変換する設計にすると、一層すっきりします。

⏩ Prolog のパターンマッチは、普通の言語でいう「値を調べて分岐する」より、項どうしを一致させ、そのために変数を束縛するものです。Prolog ではこれを普通 unification（単一化） と呼びます。

例えば：

parent(taro, hanako).
parent(hanako, jiro).

ここで

?- parent(taro, X).

と聞くと、Prolog は

parent(taro, X)

と

parent(taro, hanako)

を一致させます。

結果は：

X = hanako.

です。

重要なのは、X は「値を格納する箱」というより、この式全体を一致させるために何でなければならないか決まる変数だというところです。

もう少し構造的な例：

f(a, X)

と

f(Y, b)

を単一化すると、

Y = a
X = b

になります。

つまり関数名 f が同じ、引数の個数も同じなので、引数を順に一致させる。

一方、

f(a, X)

と

g(a, b)

は f と g が違うので失敗します。

false.

になる。

Prolog らしさが分かりやすいのはリストです。

[H | T]

これは

> 先頭が H、残りが T のリスト

というパターンです。

例えば

?- [H | T] = [a, b, c].

なら

H = a,
T = [b, c].

になります。

Scheme/Lisp で言えばかなり

(car x)
(cdr x)

に近い感覚ですが、Prolog では取り出す操作を書くのではなく、構造そのものを書く。

例えば Lisp 的には：

(define (first x)
  (car x))

ですが、Prolog なら：

first([H | _], H).

です。

これは

> first の第1引数が「先頭 H、残りは何でもいいリスト」なら、第2引数は H

という関係を宣言しています。

だから、

?- first([10,20,30], X).

で

X = 10.

になる。

ここで _ は「何でもいいし、その値には興味がない」という匿名変数です。

さらに面白いのは、Prolog のパターンマッチは方向がないことです。

first([H | _], H).

に対して

?- first(X, 10).

と聞くこともできます。

すると例えば：

X = [10 | _].

つまり、

> 「先頭要素が10になるリストとはどんなものか？」

を逆向きに解ける。

これが通常の関数型言語の pattern matching との大きな違いです。

ML/Haskell なら例えば：

first (h:_) = h

は基本的には

入力 → 分解 → 出力

ですが、Prolog は

first(List, Element)

という関係なので、

List → Element
Element → List
両方指定して検査

の全部に使える。

たとえば：

append([], Ys, Ys).
append([X|Xs], Ys, [X|Zs]) :-
    append(Xs, Ys, Zs).

これはリスト連結です。

普通に：

?- append([a,b], [c,d], X).

なら

X = [a,b,c,d].

ですが、

?- append(X, Y, [a,b,c]).

とすると、

X = [],
Y = [a,b,c] ;

X = [a],
Y = [b,c] ;

X = [a,b],
Y = [c] ;

X = [a,b,c],
Y = [].

と、**「[a,b,c] を前半と後半に分ける方法を全部出せ」**としても動く。

ここが Prolog の核心にかなり近いです。

なので、Prolog を理解する時には

関数

ではなく

関係 + パターンマッチ + 探索

と思うといいです。

そして実際には、

head([H|_], H).

の左辺そのものがパターンで、

[H|_]

が Lisp の cons セル構造をそのまま記述している、と見るとかなり分かりやすい。

あなたの馴染みの Lisp 寄りに無理やり書けば、Prolog の

member(X, [X|_]).
member(X, [_|Xs]) :-
    member(X, Xs).

は概念的には

member(X, cons(X, anything)) = true

member(X, cons(anything, Xs)) =
    member(X, Xs)

です。

ただし X が「入力値」だとは限らない。同じ変数名が出てくる場所を全部同じものにしろ、という制約になっています。

この「代入ではなく同一性の制約」という感覚を掴むと、Prolog は急に分かりやすくなります。

CSGの典型形

α A β → α γ β

を見て「これじゃないか」と思ったのは、おそらくここだと思う。

A 単独では書き換えられず、Aが置かれているコンテキストを見て遷移可能性が決まる。

君の場合も、

AST-node + scope-context
             ↓
          PST-node

だから非常によく似ている。

ただ、重要な違いが一個ある。

古典的CSGの α と β は基本的に同じ文字列上の周囲なんだ。一方、君のcontextは文字列上の隣接物ではなく、

current frame
    ↓ parent
outer frame
    ↓ parent
outer frame
    ↓
global

という環境の連鎖になっている。

だから、

α A β

より君のPST変換を正確にモデル化するなら、

⟨Γ, A⟩ → ⟨Γ, P⟩

と書くほうが近い。

例えば、

Γ = [
    { y : float },
    { x : int },
    { x : char* },
    global
]

なら、

⟨Γ, identifier(x)⟩
        ↓
⟨Γ, variable(x, int, frame=1)⟩

になる。

そして君が言った

> 新しいスタックフレームが積まれては降ろされる。その途中の任意の変数が正当だったりそうでなかったり。

ここはさらに面白い。

例えばAST走査中に、

{
    int x;
    {
        float y;
        x + y;
    }
}

なら変換器自身の状態が、

push {x:int}

    push {y:float}

        lookup x → outer frame
        lookup y → current frame
        x+y の型を決定

    pop {y:float}

pop {x:int}

と変化する。

つまりPST生成は単純な

AST → PST

じゃなくて、実態としては

(AST, Γ) → (PST, Γ')

という状態付き書換えなんだよな。

ここまで来ると、俺なら「CSGでPSTを作る」というアイデアを少し言い換える。

CSGそのものをパーサとして使うというより、CSGの「書換え可能性がcontextによって決まる」という思想を、スコープ環境Γを持つAST→PST書換え器に使う。

そして、君のカスケード・ハッシュテーブルは、その Γの実装そのもの と考えられる。

これは相当きれいだ。

CST
 │ CFG
 ▼
AST
 │
 │  Γ = cascade hash tables
 │  ├─ declarations
 │  ├─ types
 │  ├─ bindings
 │  └─ scopes
 ▼
PST

という姿になる。

だから最初の「あらかじめ宣言されてる型はコンテキストだろう？」より一歩進めて、

型だけじゃない。君のカスケード・ハッシュに入っている「現在そのASTノードから見える世界」全体がcontextだ。

ということになる。

そしてこれなら「途中の任意の変数が正当かどうか」という判定そのものが、context-sensitive なマッチ条件になる。たとえば規則を

identifier(?x)
    where lookup(Γ, ?x) = ?binding
→
bound-variable(?binding)

と書ける。

逆に lookup が失敗すればその規則は適用不能。

これ、君が作ろうとしていたパターンマッチジェネレータとPST生成がかなり自然につながるところだと思う。

🎯 テンプレートってCFGじゃないんだろ？カスケード・ハッシュは役に立つか？

🎯 First Lambda が関数呼び出しとかでなくせいぜい clause をジャグリングするだけなら「逆コンパイルは永久ループにはならない」と思う。

⏩ うん、その条件ならかなり強く言える。First Lambda の逆変換が停止することを、変換規則の設計で保証できる可能性が高い。

ポイントは、First Lambda が一般の関数評価ではなく、

if (...) A else B

を例えば

IF(cond, λ.A, λ.B)

のようにclause の配置・包含関係を組み替えるだけなら、変換時に新しい計算を始めているわけではないこと。

特に逆コンパイル規則を、

FirstLambda node → source-language control structure

の一方向に限定し、逆変換によって新しい First Lambda node を増殖させないようにすればいい。

停止性は「サイズ」より、例えば未処理ノード数を測度にすると綺麗。

μ(PST) = 未逆変換の First Lambda ノード数

各規則について必ず

μ(after) < μ(before)

なら、自然数上の狭義減少だから永久ループは起きない。

例えば、

FL_if(C, A, B)
    ↓
if (C) A else B

で FL ノードが1個消える。AやBの内部にもFLがあれば再帰的に処理するけれど、親を展開したことで新しいFLを作らない。

これは重要で、

FL_A → FL_B
FL_B → FL_A

みたいな一般の項書換え系なら当然ループできる。

でもFirst Lambdaを

> clauseを束ねたり並べ替えたりするためだけの有限個の構造ノード

に制限すれば、

PST
 ↓
FLを1個消費
 ↓
FLを1個消費
 ↓
...
 ↓
対象言語AST/CST

という消費型の逆変換にできる。

さらに君の構想では面白い副作用がある。逆コンパイラで関数を実行する必要がない。

たとえばwhileを意味的に

while(C, B)

という特殊なFirst Lambdaで保持していても、逆変換器はwhileの意味を実行しない。

WHILE(C, B)
    → tokens("while", "(", C, ")", B)

と構造を戻すだけ。

元プログラムが

while (1) { ... }

という永久ループでも、逆コンパイラ自身は永久ループしない。プログラム中のループと、変換器のループは完全に別物だからね。

ここはかなり大事な区別になる。

だからFirst Lambdaに課す制約として、

1. clauseを子として持つ
2. clauseを実行しない
3. 逆変換時に自分と同等以上の抽象ノードを生成しない
4. 各逆変換で「未変換FL数」などの測度が必ず減る

くらいを決めておけば、逆コンパイルの停止性を設計上証明できる。

これはFirst Lambdaのかなり魅力的な性質だと思う。一般的な「高級言語→低級表現→高級言語」は元の構造を失って曖昧になるけど、First Lambdaが単なるclause topology の正規化なら、情報を保存したまま往復できる余地が大きい。

要するに、First Lambdaを「計算機構」として強くしすぎないことが、逆に武器になる。弱いから逆に戻せる。

🎯 m68kにプラマイ何ビット分までみたいなレジスタ相対アドレッシングがあったろ。構造体メンバのオフセットの解決をコンパイル時ではなくリンク時まで遅らせる際に悩ましいのはこのディスプレースメントの範囲だ。この問題を「逆コンパイル」で解決したい。

⏩ そういう用途なら「逆コンパイル」はかなり相性がいいと思う。

まず確認すると、素の68000では典型的な

move.l  12(a0),d0

の 12(a0) は 16-bit signed displacement なので、おおむね -32768..+32767 の範囲。インデックス付きの古い形式では displacement が8-bitのものもある。68020以降はアドレッシングが拡張され、より大きな base displacement も扱える。

で、君の問題はこうだよね。

struct S {
    ...
    int x;
};

p->x

普通ならコンパイル時に

offsetof(S,x) = 120

を決めて、

move.l 120(a0),d0

を吐く。

ところが構造体レイアウトをリンク時まで遅延させたいなら、コンパイル時には

offsetof(S,x) = ?

なので、この命令を最終決定できない。

もっと悪いことに、リンク時に

offsetof(S,x) = 20000

なら16-bit displacementに入るが、

offsetof(S,x) = 50000

なら入らない。

つまりこれは単なる relocation の

??? → 50000

という数値の穴埋め問題ではない。

命令そのものを

move.l disp(a0),d0

から例えば

move.l #50000,d1
move.l (a0,d1.l),d0

のような別系列へ変えなきゃいけない可能性がある。

ここで「逆コンパイル」が効いてくる。

コンパイラが最初から

move.l ??(a0),d0

みたいな半完成機械語をリンク可能オブジェクトとして保存するのではなく、

LOAD_MEMBER
    base = p
    type = S
    member = x
    result = ...

という高位の意味を残しておく。

そしてリンク時に、

S.x → offset 50000

が確定したところで、もう一度コード生成する。

つまり、

source
  ↓
AST
  ↓
PST
  ↓
IR
  ↓
provisional machine code

まで行ったものを、必要な部分だけ

machine code
   ↑ 逆コンパイル
IR / PST
   ↓ linkerで確定したlayout
machine code

と戻して再生成する。

これなら displacement overflow はリンクエラーではなく、コード選択のやり直しになる。

たとえばリンク前には、

member_load(p, S::x)

という意味しか確定させない。

リンク時、

offset(S::x) = 120

なら

move.l 120(a0),d0

を選ぶ。

一方、

offset(S::x) = 50000

なら別の合法な命令列を選ぶ。

さらに極端には、

offset(S::x) = 0

なら

move.l (a0),d0

に縮められる。

つまりリンク時にやりたいのは relocation より強い。

relocation

instruction + unknown integer
             ↓
instruction + known integer

ではなく、

late instruction selection

semantic operation + final context
             ↓
best legal instruction sequence

だと思う。

そして、これを君のFirst Lambda/PSTの話につなげるとかなり面白い。

構造体アクセスをPSTで

(member-ref
    object=p
    owner=S
    member=x)

として残しておけば、リンク時に必要なのは offsetof(S,x) というcontextを追加するだけ。

Γlink:
    sizeof(S)       = ...
    alignof(S)      = ...
    offsetof(S,x)   = 50000
    ...

それをPST→機械語コードジェネレータへもう一度食わせる。

だから俺なら、「全部を機械語から逆コンパイルする」というより、機械語にPSTへ戻れるパンくずを残す設計にする。

例えばオブジェクトファイル中に、

.text
    仮コード

.rewrite
    address=0x1234
    length=4
    pst-expression=(member-ref S x A0)

みたいな情報を持つ。

リンク時に、

この relocation は収まる？
        │
   yes ─┴─ no
   │       │
patch    PSTへ戻す
            ↓
       instruction select
            ↓
       新しい命令列

とする。

実はここで普通のリンカにある relaxation と親戚になる。分岐距離などが確定したあと、短い形式・長い形式を選び直す発想は既にある。ただ君の案はもっと一般的で、リンク時relaxationを「意味レベルまで逆コンパイルして再コンパイルする」方式へ一般化することになる。

これなら構造体メンバだけじゃない。

branch displacement
global variable addressing
vtable / method slot
structure member offset
TLS offset
small-data addressing
PC-relative addressing

なんかを全部、

「リンク時に具体値が判明するまでは、
 命令形式を確定しない」

という一つの原理で処理できる。

そして68000はこの実験にはかなり面白い。同じ意味のメモリアクセスについて、短いdispを使える場合と使えない場合でコード形状そのものが変わるから、「普通のrelocationでは足りない」ことが非常に分かりやすく出る。

要するに君の「逆コンパイル」は、

という普通の逆コンパイルではなく、

みたいなアドレス表現型を持たせる。つまり、

ptr<T>     = 意味論上のポインタ
addr16     = 16bitの機械アドレス値

を分ける。

これがZ80みたいな機械で効く。

Z80なら概念的には、

data width    = 8
address width = 16

なので、

u8
u16
ptr<u8>

は普通に使える。一方で

u32
u64

はネイティブレジスタ一個には乗らない。

でも架空RISCでは無限レジスタだから、

%1 : u32

と書けてもいい。

バックエンドが

%1.lo0 : u8
%1.lo1 : u8
%1.hi0 : u8
%1.hi1 : u8

みたいに分解する。

ただしここで重要なのは、「表現できる」と「実用的に実行できる」は別ということだね。

UTF-8デコーダなんかは非常に良い例で、ほとんど

u8
u16程度のカウンタ
ptr<u8>
比較
AND/OR/shift
load/store
branch

しか要らない。

だから、

UTF8 decoder
      ↓
typed infinite-register IR
      ↓
Z80

はかなり自然に落とせる。

例えば

if ((c & 0xe0) == 0xc0)

なら架空RISCで

%c    : u8   = load %p
%a    : u8   = and %c, 0xe0
%cond : bool = eq %a, 0xc0
branch %cond, L2, Lnext

程度。

Z80では bool レジスタなんて作らず、フラグへ吸収すればいい。

AND E0h
CP  C0h
JR  Z,L2

という具合。

ここで架空RISCの設計思想がかなり見えてくる。

型の幅は「ソース上必要な意味の幅」であって、「ターゲットのレジスタ幅」ではない。

だから、

u1 / bool
u8
u16
u32
u64
...
ptr<T>

は持ってよい。

その上でターゲット記述に、

native integer widths: 8,16
address width: 16
cheap operations: u8
expensive operations: u32
unsupported primitive: u64 multiply

などを書く。

するとコンパイル可能性にも段階を付けられる。

native
legalized
library-lowered
impossible

例えばZ80なら、

u8 add       → native
u16 add      → native-ish
u32 add      → legalized into several ops
u32 divide   → runtime/library
flat ptr32   → impossible under plain 64 KiB model

という感じ。

そして君が言うDSPやオールディスクリート回路まで考えるなら、これがさらに面白くなる。

DSPなら逆に、

i16
i24
i40 accumulator
fractional
saturating
vector

みたいな変なネイティブ型があるかもしれない。

しかし架空RISC側には、

mul
add
shift
saturate
load

などの意味があればよく、ターゲットが

mul + add

を一命令のMACに潰してもいい。

オールディスクリート回路ならもっと極端で、

8bit CPU

ですらなく、

この回路は8bit XORとrotateとtable lookupだけ異様に速い

という世界でもいい。

そこで架空RISCから命令を選ぶというより、

IR graph
   ↓
pattern matching
   ↓
available hardware primitives

になる。

つまりこれはだんだん「RISC」というより、

型付きデータフロー言語 + 制御フロー

に近くなる。

そしてたぶんその方が、君の狙っている「未知CPU」には強い。

ポインタについても同じで、

ptr<T>

を最初から「整数アドレス」と決めない方がいい。

将来あるいは特殊機械では、

segment:offset
bank:pointer
capability
object handle
word address
byte address

かもしれないから。

なので最低でも、

ptr<T, address-space>

くらいにはしておくといい。

例えばZ80なら、

ptr<u8, main16>
ptr<u8, io>

DSPなら、

ptr<i16, program>
ptr<i16, data>

みたいにできる。

要するに、p32/p64 は物理表現としては必要だが、意味型の最上位には置かない。

ptr<T>
   ↓ lowering
addr16 / addr32 / capability / banked-address / ...

という分離が、未知CPUまで射程に入れるなら一番強い。

そしてUTF-8デコーダのような「小さい意味論だけで書けるコード」を、この架空機械の最初の実験台にするのはかなり良いと思う。Z80、DSP、変な自作CPUの三つに同じIRを落とせたら、この設計が本当にISAから独立しているかかなり分かる。

🎯 データセンターとかにはCPUを問わず走るコードのニーズがあるんだろ？一方俺はフォン・ノイマン型とデータフロー型の両方を「並列に行える限りバラバラにしておけ」と。

⏩ ある。今のデータセンターでは x86-64だけを想定してバイナリを配ればよい、という前提はかなり弱くなっている。Kubernetes自身も複数CPUアーキテクチャ向けイメージを扱うし、WebAssembly/WASIはまさに「ホストCPUやOSから実行コードをある程度切り離す」方向を狙っている。LLVMもターゲット非依存コード生成を明確に持つ。

ただ、君が今言っているものは、その「portable bytecode」より一段面白い。

普通の仮想ISAは、

portable program
      ↓
仮想的な逐次CPU
      ↓
x86 / ARM / ...

になりやすい。つまりCPUを抽象化したつもりでも、フォン・ノイマン型CPUという前提までは引きずっている。

君の

> 並列に行える限りバラバラにしておけ

を原則にすると、むしろこうなる。

dependency graph
       /    /    \     \
     op   op     op    op
      \   /       \    /
       op           op
         \         /
             op

命令列が第一ではなく、依存関係が第一。

例えば普通なら、

a = load p
b = load q
c = a + 1
d = b * 2
e = c + d

と並べるところを、

%a = load %p
%b = load %q

%c = add %a, 1
%d = mul %b, 2

%e = add %c, %d

と持つ。

ここで記述順には意味を持たせない。

依存関係だけなら、

load p ─→ add 1 ─┐
                 ├→ add
load q ─→ mul 2 ─┘

だから最初の二つは並列、次の二つも並列。

これなら同じIRをフォン・ノイマン機にもデータフロー機にも落とせる。

フォン・ノイマンCPUではバックエンドが勝手に順序を付ける。

load a,p
add  a,1
load b,q
mul  b,2
add  a,b

OoO CPUならCPU自身が再び依存グラフを発見して並列実行する。

一方、本物のデータフロー機なら、

operand ready
      +
operand ready
      ↓
fire

としてそのまま走らせればいい。

FPGAならさらに露骨に、

load-unit ─ add-unit ─┐
                      ├ add-unit
load-unit ─ mul-unit ─┘

という回路になる。

ここで非常に重要になるのが、さっきの 「副作用を明示する」 だと思う。

純粋な

%c = add %a, %b

なら好き勝手にバラせる。

ところが、

store p, x
store p, y

は順序を勝手に変えられない可能性がある。

だから副作用にも依存線を引く。

%M1 = store %M0, %p, %x
%M2 = store %M1, %p, %y

のようなmemory tokenでもいい。

すると、

値依存
制御依存
メモリ依存
I/O依存

以外には原則として順序が存在しない。

これは君の言葉なら本当に、

> 並列に行える限りバラバラにしておけ

になる。

しかもこれ、「フォン・ノイマン型にも対応する」というより、

フォン・ノイマン型を、依存グラフに任意の合法的な全順序を付けた特殊ケースとして扱える

んだ。

partial order
    ↓ scheduling
total order
    ↓
von Neumann CPU

一方、

partial order
    ↓
ほぼそのまま
dataflow machine

になる。

ここは設計原理としてかなり強い。

そして現在のOpenXLA/StableHLOがML領域でやっていることにも近い部分がある。StableHLOは異なるフレームワークとコンパイラの間のportable operation setとして設計されており、特定CPUの命令列ではなく、より高位の演算を保持する。

ただ君の場合はML専用でなく、

integer
pointer
memory
branch
call
I/O

まで含む一般計算用にしたいわけだ。

そう考えると、さっき言った「無限個の型付きレジスタ」も、実はさらに一歩進めて、

%17 : i8

を「レジスタ」と呼ぶ必要すらないかもしれない。

単に、

%17 : i8 = xor %12, %15

という値の名前。

物理レジスタは一切存在しない。

バックエンドが、

CPU      → register
Z80      → AとかHLとかmemory temporary
GPU      → lane register
dataflow → token
FPGA     → wire/register

へ割り当てる。

そうすると架空RISCの核心は、

命令セットではなく、型付き値と依存関係のグラフ

になってくる。

俺なら今のところ、

Typed values
+
Operations
+
Explicit effects
+
Dependency edges
+
Control-flow regions

この5つを最小核にする。

「RISC」という名前を残すとしても、実体はかなり Dataflow-RISC だね。

そしてこれはデータセンター用途とも相性がいい。CPUアーキテクチャを越えるだけでなく、将来的には「この仕事はCPU、この部分はGPU、この部分は専用アクセラレータ」という分割まで同じ表現からできる可能性がある。実際、現在のサーバー側でもWasmのようなportable execution layerや、OpenXLAのようなハードウェア非依存寄りの中間表現が使われる方向は既に存在する。

だから君の原則はかなり簡潔に書けると思う。

順番は意味ではない。依存だけが意味である。順番が必要な機械に落とすときだけ順番を作る。

これならフォン・ノイマンとデータフローを同じ側から眺められる。

🎯 カスケードハッシュはスコープを出る際に必ずデリートするかというとそんなことはなくてデリートしないまま次のスタックフレームを親フレームにリンクすることもできる。つまり木構造のスコープ一覧が得られる。これはRustのメモリ安全みたいに何かを安全にすることはできないかな？

⏩ できる。かなり面白い。「消さないカスケード・ハッシュ」は、単なる名前解決表ではなく、スコープ／リージョンの永続的な木になる。そこに「どの値がどのスコープで生まれ、どこへ逃げ、いつまで参照可能か」を載せれば、Rustに近い種類の安全性を静的に検査できる。

たとえば、

global
└─ frame A
   ├─ frame B
   │  └─ frame C
   └─ frame D

をコンパイル後も保存しておく。各変数に、

x:
    declared_in = B
    type = T
    storage = stack

のような情報を持たせる。

するとC内で、

p = &x

は合法。CはBの子だから、Bで生きている x が見える。

ところがBの外側、例えばAへ &x を持ち出そうとすると、

lifetime(p) > lifetime(x)

になり得る。

木で見るとものすごく単純で、

x belongs to B

reference created in C
        ↓
reference escapes to A

なら、

A is ancestor of B

だから参照の生存範囲の方が所有物より広い。

禁止。

これはregion-based memory safetyとしてかなり直接的に表現できる。

Rust風に書くなら、

'x = lifetime of frame B
'p = lifetime required by destination A

について

'p ⊆ 'x

でなければいけない。

君の木構造なら、この包含関係を「祖先・子孫関係」でかなり自然に扱える。

さらに面白いのは、ポインタに単なる

ptr<T>

ではなく、

ptr<T, frame=B>

みたいなprovenanceを付けられること。

例えば、

%p : ptr<int, B>

なら、

> このポインタはB以下でしか安全にdereferenceできない

とPSTに残せる。

そうするとPST生成時に、

dereference(%p) at frame C

なら

C descendant-of B
→ OK

一方、

dereference(%p) at frame A

なら

A descendant-of B
→ false
→ invalid

となる。

これだけでも、

use-after-scope
dangling stack pointer
一部のuse-after-free
無効なクロージャcapture

を捕まえられる。

そして、ここからクロージャが非常に面白くなる。

function outer() {
    int x;

    return lambda() {
        return x;
    };
}

普通のスタック変数として x を持つなら、

outer frame
└─ lambda frame

でlambdaがouterより長生きするから、そのままでは駄目。

でもコンパイラが、

x:
    storage = heap/environment

へ昇格させればよい。

つまりスコープ木を見れば、

reference escapes owner frame
        ↓
stack allocation impossible
        ↓
promote to closure environment

というescape analysisもできる。

ここまでならGCなしでもかなり安全にできる。

そしてRustっぽくするなら、さらにハッシュ表のエントリへ状態を載せる。

x:
    owner = B
    state = alive
    shared_borrows = {...}
    mutable_borrow = none

として、

&x

でshared borrow、

&mut x

でexclusive borrowを登録。

すると、

shared borrow中
    ↓
write x

は禁止、

mutable borrow中
    ↓
別のborrow

も禁止できる。

ここで面白いのは、Rustのborrow checkerをそのまま真似しなくても、君のデータ構造では

「名前表 + スコープ木 + 値の状態」

が最初から一体化していること。

たとえば、

Frame B
hash:
    x → {
        type: int
        owner: B
        state: alive
        loans:
            shared → C1,C2
    }

みたいにできる。

そしてスコープを抜けたとき、実際にはframeをdeleteしない。

代わりに、

B.status = closed

とする。

するとコンパイラの後段から見ても、

x existed
x belonged to B
B ended here
pointer p escaped from B

という履歴が全部残っている。

これはかなり大きい。

削除しないことで、scope tableが「現在の環境」から「プログラム全体の生命期間グラフ」になる。

だから俺なら、カスケードハッシュを二つの役目にする。

lookup chain
    → 名前解決

persistent scope tree
    → lifetime / ownership / escape / provenance analysis

さらに、前に話していたPSTとも非常によく合う。

ASTで、

address-of x

だったものをPSTでは、

address-of {
    object = B::x
    region = B
    mutability = shared
}

まで具体化できる。

つまりPSTのPは「particular」だとするなら、型だけでなく所有リージョンまでparticularになる。

ただし一つ大事なところがある。

木を保存するだけではRust級の安全性にはならない。

木から得られるのは主に、

lexical lifetime / region containment

だから、

malloc/free
aliasing
move
interior pointer
shared mutable state
thread

まで安全にしたければ、ポインタや値に追加の状態・規則がいる。

でも逆に言えば、かなり良い土台にはなる。

俺なら最初の目標として、

> スタック由来ポインタは、そのowner scopeの子孫スコープでしかdereferenceできない

という規則を一個入れる。

それだけでCでは普通に起こる、

int *f(void)
{
    int x;
    return &x;
}

を、カスケードハッシュの木だけでかなり綺麗に弾ける。

そしてそこから move、borrow、escape を一つずつ足していけば、**「Rust文法ではないが、Rust的な安全性を持つPST」**という方向が見えてくる。

🎯 数値系、文字列、俺はハッシュテーブルのサブシステム化に興味がある。究極IRの前に「データフロー型 Lisp Machine」「とそのソースコード」を考えよう。

⏩ いい。これは究極IRを先に抽象論で決めるより、**「実際に一台の変なLisp Machineを設計して、そのソース言語から逆算する」**方が筋がいい。

俺ならまず、データフロー型 Lisp Machine の核をこう置く。

(let ((a (+ x y))
      (b (hash-get table key))
      (c (utf8-decode stream)))
  ...)

普通のLispなら見た目として上から順に評価されそうだけど、この機械では原則、

(+ x y)             数値サブシステム
(hash-get table key) ハッシュサブシステム
(utf8-decode stream) 文字列サブシステム

を依存がない限り同時に投げる。

つまりS式は「命令列」ではなく、

operation + operands + dependency

を記述する構文になる。

そして君が興味を持っている

数値系
文字列系
ハッシュテーブル系

を、ライブラリではなく計算サブシステムとして扱う。

たとえば、

┌─ Numeric Engine
Lisp Machine ─┼─ String Engine
              ├─ Hash Engine
              ├─ Memory Engine
              └─ Control / Scheduler

みたいな構成。

ここでCPU本体が

ADD
MUL
LOAD
STORE

を全部実行する必要がない。

例えば、

(hash-ref env 'foobar)

という式が来たら、Hash Engineへ

LOOKUP
 table = env
 key   = "foobar"

というtokenを流す。

結果tokenが帰ってきたら、その値を待っていたノードだけ発火する。

Lispとの相性がすごくいい

S式なら、

(+ (* a b)
   (* c d))

は最初から木になっている。

これを逐次命令列へ潰さず、

a ─┐
   MUL ─┐
b ─┘    │
        ADD → result
c ─┐    │
   MUL ─┘
d ─┘

として保持する。

二つの MUL は当然並列。

つまり、コンパイラが苦労して「並列性を発見する」のではなく、

最初から依存関係しか書かない。

これは前に話した

> 順番は意味ではない。依存だけが意味。

を、そのままソース言語まで持ち上げた形になる。

ただしLispには副作用がある。

(set! x 10)
(print x)

ここだけは、

set! → print

という依存を明示しないといけない。

だからこのLisp Machineでは、副作用もtokenにするのが綺麗。

(let ((m1 (store m0 x 10))
      (m2 (print m1 x)))
  m2)

実際のソースではこんな露骨に書かなくてもいいが、内部的には

memory-state
io-state
hash-state

のようなeffect tokenを流す。

すると純粋な計算は完全にバラせる。

は実行時には

SYMBOL #39182

      ↓

みたいなprimitiveを持つ。

ただしソース言語としては、

だけ。

ハードウェア実装がなければ普通のコードへloweringすればいい。

String Engineあり
    → hardware execution

なし
    → Lisp implementation

を全部「CPU命令」とは考えない。

ただ、この機械で特に面白いのは 関数呼出しをどうするか だと思う。

普通のLisp Machineなら、

(f a b)

はcall。

でもデータフロー機なら、

f
a
b
↓
apply node

という一個のノードに過ぎない。

しかも f が純粋なら、その内部も即座に展開してdependency graphへ混ぜてよい。

例えば、

(defun f (x y)
  (+ (* x x) (* y y)))

に対して、

(f a b)

を

a → MUL ─┐
         ADD
b → MUL ─┘

まで展開できる。

つまりinlineが特別なoptimizationではなくなる。

逆に「展開しない関数」が特殊になる。

ここでFirst Lambdaも綺麗に入ってくる。

例えば、

(if c
    (foo)
    (bar))

なら if をCPUのbranchとして早々に潰さず、

c
          ↓
       selector
       /      \

というclause selectorとして保持する。

これならFirst Lambdaが本当に「clause juggling」だけになる。

(while c body)

ではなく、

predicate clause

feedback edge

としてデータフローグラフになる。

だからこのLisp Machineは、

First Lambdaを制御構造のハードウェア抽象として試す実験台

にもなる。

を一個のオブジェクトにしている。

までしか言わない。

     \

R2: g (b) -> x

             ├── x ──> R3
       R2 ──┘

R3 が読む x はどちらなのか。

普通の命令型言語なら「ソースコード上で後に書いた方」と決める。しかしこの Request 言語ではもともと順序を書いていない。

なら、

> 順序を書いていないのに、順序によって結果が変わるプログラム

はコンパイルエラーにしてしまえる。

これはかなり強い性質です。

つまり「並列化可能か」をコンパイラが頑張って推測する従来型とは逆で、

> プログラムは本来 unordered。必要な順序だけ依存関係として記述する。

となる。

そして物理的に並列に動かせなければ scheduler が勝手に sequential に落とす。

ここで区別すると綺麗です。

logical ordering
    ≠
physical serialization

A → B は論理的な依存。

一方、

A || B

なのに演算器が一個しかないから

と実行するのは、単なる物理的 serialization です。プログラムの意味には入ってこない。

という位置づけにできる。

Inline Functions as Syntax

― 文法としてのインライン関数 ―

---

要旨

本稿では、即時実行されるラムダ式（いわゆる IIFE: Immediately Invoked Function Expression）を単なる関数適用ではなく、構文として解釈する枠組みを提案する。これにより、let や while といった制御構造をマクロ展開に依存せず、関数記述のみで表現する可能性を検討する。
本手法は「関数」と「構文」の境界を再定義し、構文拡張の基盤を単一の仕組みに統合する試みである。

---

1. 背景と問題意識

多くの関数型言語、特に Lisp 系言語においては、新たな構文を導入するためにマクロシステムが用いられる。マクロは強力である一方で、

評価系とは別のメタレイヤーを導入する

展開規則の理解が必要になる

衛生性（hygiene）などの問題が生じる

といった複雑性を伴う。

一方で、関数適用そのものはすでに言語の中核に存在しており、これを用いて構文的役割を担わせることができれば、より単純な体系が得られる可能性がある。

本稿ではこの観点から、「インライン関数を構文として扱う」という再解釈を提案する。

---

2. 基本アイデア

出発点は次の形である：

((lambda ...)

これは通常、ラムダ式によって生成された関数オブジェクトを即座に適用する式として解釈される。

しかし本稿では、この評価モデルを変更し、

> 「ラムダ式が生成する関数をオブジェクトとして扱うのではなく、呼び出し位置にインライン展開される構文として扱う」

という再解釈を行う。

このとき、ラムダ式は値ではなく、構文的テンプレートとして振る舞う。

---

3. 文法としてのインライン関数

この再解釈の下では、いくつかの基本構文が自然に表現できる。

3.1 let の再表現

(let ((x v)) body)

は、

((lambda (x) body) v)

と等価であることはよく知られている。

ここでさらに一歩進めて、これを単なる関数適用ではなく「構文」とみなすことで、let は新たな構文ではなくインライン関数の特殊形と捉えられる。

---

3.2 制御構造の記述

同様に、ループや条件分岐も再帰や遅延評価を用いて記述可能である。

例えば while 的な構造は、自己再帰するラムダとして記述できる：

((lambda (loop)
   (loop loop))
 (lambda (self)
   (if cond
       (begin body (self self))
       #f)))

このような構造は通常「高階関数によるエンコーディング」と見なされるが、本稿の立場ではこれを構文の一種として扱う。

---

4. マクロとの関係

本手法はマクロの代替となる可能性を持つが、完全な置き換えではない。

マクロが持つ特徴：

任意の構文変換が可能
コンパイル時に実行される

に対し、本手法は：

評価規則の再解釈に基づく
単一の構成要素（ラムダ）に統一される

という特徴を持つ。

したがって本手法は、

> 「構文拡張を関数機構へ還元するアプローチ」

と位置付けられる。

---

5. 技術的課題

このアプローチには未解決の問題が存在する：

評価順序の定義
インライン展開と通常評価の整合性

変数捕捉（variable capture）
マクロと同様の衛生性問題

最適化との関係
インライン化とコンパイラ最適化の境界

意味論の定式化
これは単なる変換規則なのか、新しい評価戦略なのか

これらは今後の検討課題である。

---

6. 結論

本稿では、即時実行されるラムダ式を構文として扱う「Inline Functions as Syntax」という考え方を提案した。

このアプローチは、

関数と構文の境界を曖昧にする
マクロに依存しない構文表現の可能性を示す
言語の最小コアを再検討する契機となる

という意義を持つ。

今後は形式意味論の確立および実装による検証が必要である。

🎯「継続（コンティニュエーション）は任意の制御構造を書くことができる」。👈こういうことシレッと言うわけですよ。継続ってマルチタスクOSがタイムシェアリングのために持つCPUコンテクストみたいなもんですよ？任意の制御構造を書けるなんてそりゃ当たり前です。制御構造どころか他のスレッドや他のプロセスにまでも自由に飛べるスペックなんですから。じゃあせいぜい任意の制御構造が書けさえすればいいだけなら何しか要らないか。その答えがファーストラムダなんです。

⏩ それ、かなり強い言い方にできます。

「継続で任意の制御構造が書ける」という説明は、たしかに強すぎる道具を持ち出して弱い結論を言っている感じがあります。

継続は要するに、

> 「今この瞬間の“残りの計算”を値として捕まえて、あとでそこへ飛べる」

というものだから、OSでいえばユーザ空間の関数呼び出しどころではなく、実行コンテクストそのものを持ち運ぶ発想に近い。だから loop も break も exception も coroutine も generator も backtracking も、理屈の上では書ける。そりゃそうだ、という話になる。

でも問題はそこじゃない。

あなたの言う「ファーストラムダ」は、たぶんこういう切り分けです。

> 任意の制御構造を書くために、継続ほど強いジャンプ能力は要らない。
必要なのは、評価を遅らせたコード片を引数として渡し、それを呼び出し側にインライン展開できる保証である。

つまり、

(if condition
    (lambda () then-body)
    (lambda () else-body))

みたいなものを本当に制御構造として使いたいなら、必要なのは「継続」ではなく、

1. then/else を普通の値として即時評価しないこと

2. それらを関数として渡せること

3. その関数呼び出しが実行時クロージャ呼び出しではなく、構文的・意味的にインライン化されること

この3つです。

だから「ファーストラムダ」の主張は、

> マクロは要らない、とまでは言わない。
しかし多くの制御構造は、マクロではなく「必ずインライン化されるラムダ」で表現できる。

という方向になる。

継続は「どこへでも飛べる」。
ファーストラムダは「ここに書いたコード片を、ここに埋め込める」。

この差は大きいです。

継続は強すぎるので、意味論も実装も重くなる。プログラムの局所性も壊しやすい。呼び出しスタック、例外、リソース解放、デバッガ、最適化、スレッド境界、全部に影響する。

一方でファーストラムダは、もっと地味で制限された道具です。でも、制御構造を書くという目的に対しては十分強い。

この言い方がいいかもしれません。

> Continuations can express arbitrary control structures because they capture the whole future of computation.
But that is overkill.
To define ordinary control structures, we do not need first-class continuations; we need first-class inline lambdas.

日本語なら：

> 継続は「残りの計算」全体を値にするので、任意の制御構造を書けるのは当然である。しかし通常の制御構造を書くために必要なのは、そこまで強い機構ではない。必要なのは、評価を遅延されたコード片を第一級の値として渡し、かつその呼び出しが実行時呼び出しではなくインライン展開として保証されることである。これがファーストラムダである。
