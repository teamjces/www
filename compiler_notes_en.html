% yc -c main.c -o main.o

🎯

main.o

🎯

PP: PreProcessor
TOK: TOKen
AST: Abstract Syntax Tree
IR: Intermediate Representation

🎯

When constructing the AST, I want to be able to say, “Oh, we already have cons cells and First Lambda.”

Apparently, an unbelievable number of compilers simply assign enum values directly to things like do-while and switch-case.

🎯

The opposite of “abstract” is “concrete,” right? Would “particular” work for “concrete”?

Since this is my system, the AST already consists only of cons cells and First Lambda. Then, after types and scopes have been resolved, does the AST become a PST?

⏩

Yes. The ordinary opposite of abstract is concrete. Particular is slightly different: it is more naturally contrasted with general, and carries the sense of “individual” or “specific.”

abstract ⇄ concrete
general  ⇄ particular

Calling the stage after the AST a PST in your own terminology is perfectly plausible, especially if you define the stages like this:

AST = a syntax tree reduced to cons cells + First Lambda
PST = the tree after type inference/checking, name resolution, and scope resolution

In that sense, Particularized Syntax Tree works fairly well. What was previously abstract syntax has now been made specific: for every identifier, “this refers to this binding” and “this has this type” have been determined.

In existing compiler terminology, this stage would more commonly be called a typed AST, resolved AST, annotated AST, or, somewhat later in the pipeline, HIR or semantic IR. PST is not a standard term, so you would be defining it as part of your own system.

With First Lambda, something like (if c a b) would already have been reduced to a very small core. Then once all type, binding, and scope information has been attached, the feeling that the tree has become “particular” rather than merely “abstract” is quite natural.

If you want the names to be symmetrical:

CST → AST → PST → IR

with PST defined as Particular Syntax Tree is an interesting choice. Here, particular means that previously unresolved semantic alternatives have been individually determined.

Higher-order inline functions and control structures

🎯

main.c
main.c,pp
main.c,tok
main.c,cst
main.c,ast
main.c,pst
main.c,ir
main.s
main.o
  • Build the CST from the tokens.
  • Look at the file extension, load the control-structure definition file for that language — though in reality it is just a set of definitions of inline functions that take inline functions as arguments — and transform the CST into the AST.
  • Resolve types, bindings, and scopes, and transform the AST into the PST.

Are there things that are “inline functions taking inline functions as arguments” but are not control structures? Or can nesting such things produce something qualitatively different?

⏩

Yes. Quite a lot of things, in fact.

Under your definition, “an inline function that takes an inline function as an argument” is essentially a higher-order inline function. That does not necessarily make it a control structure. Control structures are better regarded as one subset of that larger category.

map(xs, inline (x) { return x * 2; });

This takes an inline function, but we would not ordinarily classify map as a control structure in the same sense as if or while. The same is true of filter, fold, sort_by, and so on.

with_lock(lock, inline () {
    ...
});

with_file(path, inline (f) {
    ...
});

transaction(inline () {
    ...
});

These have the same general form. They are more naturally classified as resource management, environment control, or effect delimitation than as ordinary control structures.

with_lock(L,
    transaction(
        if_(condition,
            lambda { ... },
            lambda { ... })))

Here:

if_(condition, then_fn, else_fn)
while_(condition_fn, body_fn)
with_lock(lock, body_fn)
transaction(body_fn)

can all have almost the same AST shape:

Application
 ├─ operator
 └─ arguments
      ├─ value
      └─ Lambda

Nesting can also create genuinely new control behavior:

retry(
    transaction(
        timeout(
            lambda { ... })))

Individually these may just be higher-order operations, but their composition creates a distinctive control flow.

Inline higher-order primitive
    │
    ├── Control
    │    ├── if
    │    ├── while
    │    ├── loop
    │    └── catch
    │
    ├── Environment
    │    ├── let
    │    ├── with_lock
    │    └── with_file
    │
    ├── Collection
    │    ├── map
    │    ├── filter
    │    └── fold
    │
    └── Effect
         ├── transaction
         ├── async
         ├── retry
         └── continuation

The particularly important point is this:

What makes if special is not its syntax. What makes it special is that it controls when, and how many times, its Lambda arguments are invoked.

So from the First Lambda perspective, the essence of a control structure can be regarded as:

a higher-order function that governs the invocation policy of Lambda arguments.

TOK language and DWARF source-level debugging

🎯

After preprocessing a C source file, I tokenize it. Each token is enclosed in square brackets, and exactly one token is written per line.

[int]
[main]
[(]
[)]
[{]
[return]
[0]
[;]
[}]

I treat this token language as if it were a new programming language and build an implementation for it. At this stage it is only a mock-up: it concatenates the tokens again, reconstructs C source, passes that C source to an ordinary compiler, and obtains an executable binary.

Now let us make the binary produced from this new language source-level debuggable in GDB.

⏩

This can be done, and at the mock-up stage you do not need to generate DWARF yourself. You can let GCC do the work.

The key mechanism is #line.

#line 1 "main.tok"
int
#line 2 "main.tok"
main
#line 3 "main.tok"
(
#line 4 "main.tok"
)
#line 5 "main.tok"
{
#line 6 "main.tok"
return
#line 7 "main.tok"
0
#line 8 "main.tok"
;
#line 9 "main.tok"
}

Since newlines are ordinarily just whitespace in C, this is effectively:

int main ( ) { return 0 ; }

But every token is preceded by a #line directive telling GCC which line of main.tok the following C line logically came from.

gcc -g -O0 generated.c -o main

The resulting DWARF line table can then refer to main.tok.

(gdb) break main
(gdb) run

and GDB may display something like:

6    [return]

You can also aim for:

(gdb) break main.tok:6

The important limitation is that source lines map to machine instructions. Tokens such as ; or ) usually generate no machine instruction, so they may have no breakpoint location. That follows from the nature of the DWARF line table itself:

source location ↔ machine instruction

yacc as a precedent

🎯

yacc also emits debugging information that refers back to the original grammar definition file. The automatically generated y.tab.c contains line-control information saying that generated code came from a particular line of parse.y.

⏩

Exactly. Generated y.tab.c / *.tab.c files conceptually contain directives such as:

#line 123 "parse.y"

The pipeline is:

parse.y
   ↓ yacc
y.tab.c
   ↓ cc -g
a.out + DWARF

yet the DWARF line table can still contain mappings to parse.y.

This is not a hack. It is a long-established method for source-to-source compilers to propagate source positions from the generating language into a downstream compiler.

machine address
   ↕
IR node
   ↕
PST node
   ↕
AST node
   ↕
token
   ↕
line in main.c,tok

Prolog, unification, and decompilation

🎯 Teach me Prolog. What exactly is pattern matching in Prolog?

⏩

Prolog's “pattern matching” is more accurately called unification: making two terms agree by binding variables.

parent(taro, hanako).
parent(hanako, jiro).

?- parent(taro, X).

X = hanako.

The same idea applies structurally:

f(a, X)
f(Y, b)

unify to:

Y = a
X = b

Lists make this especially clear:

?- [H | T] = [a, b, c].

H = a,
T = [b, c].

The classic relational example is:

append([], Ys, Ys).
append([X|Xs], Ys, [X|Zs]) :-
    append(Xs, Ys, Zs).

used forward:

?- append([a,b], [c,d], X).

X = [a,b,c,d].

or backward:

?- append(X, Y, [a,b,c]).

which enumerates every prefix/suffix split.

🎯 Could this be used for decompilation?

⏩

Yes. The core idea is to describe compilation as a relation rather than a one-way function:

AST ⇄ machine code

For example:

compile(add(X, Y), Code) :-
    compile(X, CX),
    compile(Y, CY),
    append(CX, CY, C0),
    append(C0, [add], Code).

Then:

?- compile(add(const(2), const(3)), Code).

works forward, while:

?- compile(AST, [push(2), push(3), add]).

can work backward.

In realistic compilation the inverse is not unique, because optimization discards information. The more accurate question is:

Given machine code M, which IR / AST / type assignments / CFG / bindings are semantically consistent with M?

Pattern-matcher generators and CST → AST

🎯

A command such as c,tok2c,ast.exe could transform patterns like:

if, (, expr, ), clause
if, (, expr, ), else, clause
if, (, expr, ), clause, else, clause

into AST forms.

⏩

Yes. A CFG parser can do this, but a pattern-matcher generator can also do it naturally if it supports structural variables and recursive nonterminals.

if '(' $expr ')' $clause
    => If($expr, $clause)

if '(' $expr ')' else $clause
    => If($expr, Empty, $clause)

if '(' $expr ')' $clause1 else $clause2
    => If($expr, $clause1, $clause2)

The clean division is:

tok → CST
    CFG parsing is especially strong here

CST → AST
    tree pattern matching is especially strong here

tok → AST directly
    possible, but recursive nonterminals make it approach CFG parsing

Preprocessor as a rewrite-system exercise

🎯

The original concern was that an AST full of nodes such as AST_DO_WHILE, AST_SWITCH, and AST_CASE merely moves language-specific grammar categories into a tree. First Lambda is intended to reduce these into a smaller common structure.

⏩

That makes CST → AST a local structural rewriting problem, while AST → PST is context-dependent elaboration.

CST → AST
local structural rewriting

AST → PST
context-dependent elaboration

The C preprocessor is a very good test case for a generic token rewriting engine:

  1. object-like macros,
  2. function-like macros,
  3. variable-length token-sequence capture,
  4. re-emission of captured sequences,
  5. recursive rescanning.

A rule language might eventually look like:

rule object_macro
    $name
        => lookup_macro($name)

rule function_macro
    $name '(' $args... ')'
        => expand($name, $args)

At that point the system is better described as a token rewriting machine generator.

PST, context sensitivity, and cascaded hash tables

🎯 All right, then why not use CSG for the PST? Predeclared types are context, aren't they?

⏩

That intuition is good. AST → PST is context-dependent because the meaning of a node depends on an environment Γ containing declarations, types, and bindings.

Γ ⊢ x : int
Γ ⊢ y : int
----------------
Γ ⊢ x + y : int

However, classical context-sensitive grammars are narrower than what semantic analysis needs. A better implementation description is:

a context-sensitive rewrite system over tree patterns, conditioned by Γ.

pattern:
    (+ ?x ?y)

context:
    type(?x) = int
    type(?y) = int

replacement:
    (int-add ?x ?y)

🎯 You remember my cascaded hash table, right?

⏩

Conceptually:

Frame3 → Frame2 → Frame1 → Global
   ↓
 lookup(x)

A node x has no complete meaning by itself. It becomes meaningful only under the environment:

Γ3 = Frame3 → Frame2 → Frame1 → Global

A more faithful model than the classical CSG notation is:

⟨Γ, A⟩ → ⟨Γ, P⟩

Your cascaded hash table is therefore a concrete implementation of Γ.

First Lambda and terminating decompilation

🎯 If First Lambda merely juggles clauses rather than behaving as a general function call, decompilation should not fall into an infinite loop.

⏩

Yes. You can make reverse transformation terminating by construction.

Define:

μ(PST) = number of unconverted First Lambda nodes

and require every reverse rewrite to satisfy:

μ(after) < μ(before)

For example:

FL_if(C, A, B)
    ↓
if (C) A else B

First Lambda remains deliberately weak: a finite family of structural nodes that package or rearrange clauses. Its weakness becomes a strength because structural information can survive round trips.

m68k displacement and link-time re-selection

🎯

The m68k had register-relative addressing with limited displacement width. If structure member offsets are resolved only at link time, the final offset may not fit the originally chosen instruction encoding. I want to solve that by “decompilation.”

⏩

This is better viewed as late instruction selection than ordinary relocation.

semantic operation + final context
             ↓
best legal instruction sequence

Instead of retaining only:

move.l ??(a0),d0

retain semantic intent:

LOAD_MEMBER
    base = p
    type = S
    member = x
    result = ...

At link time, the final context may choose a short displacement, a longer sequence, or even a shorter zero-offset form.

does relocation fit?
        │
   yes ─┴─ no
   │       │
 patch   recover PST
             ↓
       instruction selection
             ↓
       new instruction sequence

This generalizes linker relaxation into semantic decompilation and recompilation.

Unknown CPUs and a fictional RISC

🎯 Could this really prepare us for CPUs that do not even exist yet? Could anyone have predicted Boolean registers? I want to work backward from a fictional RISC.

⏩

Yes — if the fictional RISC is not a common denominator of existing CPUs.

A value such as:

r17 : bool

should not imply any physical register class. A flags-based CPU may eliminate it, a predicate-register CPU may map it directly, and another CPU may materialize an integer.

The more useful abstraction is:

an infinite-register, typed abstract machine with explicit effects.

%1 : ptr<S>
%2 : i32 = member_load %1, S::x
%3 : bool = lt %2, 10
branch %3, L1, L2

For future hardware, the IR should preserve:

operation
inputs
outputs
types
effects
constraints

The goal is not to predict future CPUs, but to preserve enough program meaning that future CPUs can choose their own implementation.

Pointers, Z80, DSPs, and target-independent meaning

🎯 Should pointers be p32 and p64?

⏩

Better to separate semantic pointers from representation-level addresses:

ptr<T>     = semantic pointer
addr16     = 16-bit machine address representation

On a Z80-like machine:

data width    = 8
address width = 16

types such as u8, u16, and ptr<u8> are natural. Larger values can be legalized into multiple operations or lowered to libraries.

A UTF-8 decoder is a good experiment because it mostly needs simple byte-level operations, pointers, comparison, shifts, loads/stores, and branches.

The key principle is:

Type width describes the width required by source-level meaning, not the width of the target's physical registers.

Pointers should ideally support address spaces:

ptr<u8, main16>
ptr<u8, io>

or, on a DSP:

ptr<i16, program>
ptr<i16, data>

Dataflow and von Neumann machines

🎯

What I want is to treat both von Neumann and dataflow machines according to the rule:

Keep everything separate for as long as it can possibly execute in parallel.

⏩

That suggests making dependency, rather than order, the primary semantics.

load p ─→ add 1 ─┐
                 ├→ add
load q ─→ mul 2 ─┘

A von Neumann target imposes a legal total order. A dataflow target can preserve the partial order directly.

partial order
    ↓ scheduling
total order
    ↓
von Neumann CPU

Effect dependencies can be made explicit with tokens such as:

%M1 = store %M0, %p, %x
%M2 = store %M1, %p, %y

The core then becomes:

Typed values
+
Operations
+
Explicit effects
+
Dependency edges
+
Control-flow regions

Or, in one sentence:

Order is not meaning. Dependency is meaning. Introduce an execution order only when targeting a machine that requires one.

Persistent scope trees and Rust-like safety

🎯

If cascaded hash-table frames are not deleted when leaving a scope, they form a persistent tree of scopes. Can that be used for safety?

⏩

Yes. The structure becomes a region/lifetime tree.

global
└─ frame A
   ├─ frame B
   │  └─ frame C
   └─ frame D

A variable can retain metadata such as:

x:
    declared_in = B
    type = T
    storage = stack

A pointer derived from a stack object can be constrained to descendant scopes of the owner's region.

ptr<T, frame=B>

That can detect use-after-scope, dangling stack pointers, some forms of use-after-free, and invalid closure capture.

Leaving a scope need not erase history:

B.status = closed

The same structure can therefore serve:

lookup chain
    → name resolution

persistent scope tree
    → lifetime / ownership / escape / provenance analysis

A useful first rule is:

A pointer derived from a stack object may only be dereferenced within descendant scopes of the object's owner scope.

Dataflow Lisp Machine

🎯

Before designing the ultimate IR, let us think about a “dataflow Lisp Machine” and its source language.

⏩

That is probably better than inventing the ultimate IR in the abstract.

(let ((a (+ x y))
      (b (hash-get table key))
      (c (utf8-decode stream)))
  ...)

In the proposed machine, these independent operations are launched simultaneously.

                ┌─ Numeric Engine
Lisp Machine ───┼─ String Engine
                ├─ Hash Engine
                ├─ Memory Engine
                └─ Control / Scheduler

An S-expression describes:

operation + operands + dependencies

rather than a mandatory instruction sequence.

Side effects can be represented through state tokens such as memory-state, I/O-state, and hash-state.

The source language can invert ordinary Lisp's sequencing convention:

implicit parallelism
explicit sequencing

For example:

(let ((x (foo))
      (y (bar)))
  (+ x y))

allows foo and bar to run in parallel, while:

(seq
  (write-port p a)
  (write-port p b))

explicitly requests order.

Domain-specific accumulators and stateful channels

🎯

A UTF-8 decoder might use a four-byte high-speed SRAM ring buffer, returning a pointer and a valid-byte count. After consuming a three-byte sequence, it refills three bytes and continues.

UTF8 accumulator
    ring[4] : u8

The key principle is not to standardize transport between coprocessors too early. The abstract layer should constrain only:

and not:

The four-byte ring buffer is really a stateful channel:

The IR might therefore make channels first-class:

Request objects instead of continuations

🎯

A Request object contains:

  • a function pointer / closure,
  • an argument list,
  • return destination(s).

⏩

In Scheme, the core becomes:

Request = (closure, arguments, destinations)

It packages:

thing to invoke + input edges + output edges

Unlike CPS, the Request does not contain the computation to perform after the result is produced. It only says where the result goes.

A useful definition for programming-language researchers would be:

A Request is a triple consisting of a closure, a list of arguments, and a list of result destinations. Unlike CPS, it does not contain the computation to be performed after the return.

More abstractly:

Operator
Inputs
Outputs

This generalizes beyond function calls to coprocessors, remote procedures, UTF-8 decoders, and other execution units.

Scheduling Request graphs

🎯

If we create many objects consisting of an execution unit, its inputs, and its outputs, what happens when they cannot execute in parallel?

⏩

Build a dependency graph and distinguish semantic order from physical serialization.

independent
    → parallel execution allowed

RAW: read after write
    → impose an ordering

WAW: write after write
    → serialize if semantics determine an order;
      otherwise reject

dependency cycle
    → reject unless explicit delay/state exists

If only one execution unit is available, use a ready stack or ready queue. The same Request graph can therefore run on:

1 execution unit → sequential machine
2 units          → 2-way parallel
N units          → dataflow parallelism

The crucial distinction is:

logical ordering
    ≠
physical serialization

A cyclic graph with no initial state can be rejected at compile time as a cyclic request dependency.

Inline Functions as Syntax

— Inline Functions as Grammar —

Abstract

This paper proposes a framework in which immediately executed lambda expressions — so-called IIFEs, or Immediately Invoked Function Expressions — are interpreted not merely as function application, but as syntax.

This makes it possible to investigate whether control structures such as let and while can be expressed entirely through function notation, without depending on macro expansion.

The approach attempts to redefine the boundary between “function” and “syntax” and to unify the basis for syntactic extension under a single mechanism.

1. Background and Motivation

In many functional programming languages, particularly in the Lisp family, macro systems are used to introduce new syntactic forms.

Macros are powerful, but they also introduce several kinds of complexity:

  • they add a meta-level distinct from the ordinary evaluation system;
  • programmers must understand expansion rules;
  • problems such as hygiene arise.

Function application, on the other hand, is already part of the core language.

If function application itself could be made to play a syntactic role, it might be possible to obtain a simpler overall system.

From this perspective, this paper proposes a reinterpretation in which:

inline functions are treated as syntax.

2. Basic Idea

The starting point is a form such as:

((lambda ...)

Ordinarily, this is understood as immediately applying a function object produced by a lambda expression.

This paper instead changes the evaluation model and reinterprets the construct as follows:

Rather than treating the function produced by the lambda expression as an object, treat it as syntax that is expanded inline at the call site.

Under this interpretation, the lambda expression behaves not as a value but as a syntactic template.

3. Inline Functions as Grammar

3.1 Re-expressing let

(let ((x v)) body)

is equivalent to:

((lambda (x) body) v)

The proposal goes one step further. If the latter is treated not merely as function application but as syntax, then let need no longer be regarded as a distinct syntactic construct.

3.2 Describing Control Structures

Loops and conditional control structures can likewise be expressed through recursion and delayed evaluation.

((lambda (loop)
   (loop loop))
 (lambda (self)
   (if cond
       (begin body (self self))
       #f)))

Such constructions are normally regarded as encodings through higher-order functions. Under the position taken here, they are treated as forms of syntax.

4. Relationship to Macros

This approach may serve as an alternative to macros in some situations, but it is not necessarily a complete replacement.

Macros typically provide arbitrary syntactic transformation and compile-time execution. By contrast, this proposal is characterized by reinterpretation of evaluation rules and unification around a single primitive mechanism: lambda.

an approach that reduces syntactic extension to the function mechanism.

5. Technical Problems

Evaluation order

How should evaluation order be defined? How should guaranteed inlining interact with ordinary evaluation?

Variable capture

The approach may encounter variable-capture issues similar to those of macros. A hygiene discipline may therefore still be required.

Optimization

What is the relationship between required inline expansion and ordinary compiler optimization? Where is the boundary between semantic inlining and optional optimization?

Formal semantics

Is this merely a transformation system, or does it constitute a genuinely new evaluation strategy?

6. Conclusion

This paper has proposed the idea of Inline Functions as Syntax, in which immediately invoked lambda expressions are treated as syntactic constructs.

The approach may:

  • blur the boundary between functions and syntax;
  • permit some syntactic constructs to be represented without macros;
  • provide a basis for reconsidering the minimal core of a programming language.

Future work will require both formal semantic treatment and implementation-based evaluation.

Continuations versus First Lambda

🎯

People casually say:

“Continuations can express arbitrary control structures.”

But a continuation is basically like the CPU context that a multitasking operating system preserves for time sharing. Of course it can express arbitrary control structures. It is powerful enough to represent much more than ordinary structured control.

So if all we really need is enough power to express ordinary control structures, what is the weakest mechanism that suffices?

My answer is First Lambda.

⏩

The central claim can be stated as follows:

Continuations can express arbitrary control structures because they capture the whole future of a computation. But that is overkill. To define ordinary control structures, we do not need first-class continuations; we need first-class inline lambdas.

A continuation reifies the remainder of a computation. First Lambda is deliberately weaker: it provides delayed code fragments that can be passed as values while guaranteeing that their invocation is semantically realized as inline expansion.

The core contrast is:

Continuation:
    capture and resume the future of a computation

First Lambda:
    place a delayed code fragment here

That weaker mechanism may still be sufficient for ordinary control structures while imposing much less semantic and implementation machinery.

A more formal statement is:

A continuation reifies the remainder of a computation, and therefore naturally has enough expressive power to encode arbitrary control flow. However, ordinary control structures do not necessarily require such a strong mechanism. It may suffice to treat delayed code fragments as first-class arguments while guaranteeing that their invocation is semantically realized as inline expansion. This restricted mechanism is what we call First Lambda.
